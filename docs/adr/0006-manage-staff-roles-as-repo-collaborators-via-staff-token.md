# Manage Staff roles as repository collaborators via the Staff app token

System admins manage Staff roles directly from the Staff dashboard's Staff screen (`/staff/members`), keeping GitHub repository roles on the `reports` repo as the single source of truth. Repository **Administration: read & write** is added to the `reports-staff` GitHub App (never to `reports-bot`, which stays at `Metadata: read` + `Issues: write`), and all collaborator and invitation operations run through Admin-gated Worker endpoints using the caller's own GitHub token (`caller.token`). Management is strictly repository-scoped (by GitHub username, assigning only the three dashboard roles: Viewer → `pull`, Maintenance staff → `triage`, System admin → `admin`), with no GitHub Organization-level permissions.

## Considered Options

- **App-managed roles in Workers KV.** Rejected: breaks GitHub-enforced access on direct browser → `api.github.com` Report operations unless everyone gets Triage on GitHub or all Staff Report writes move through the Bot, and creates a second source of truth that can drift from GitHub.
- **Grant `Administration: read & write` to `reports-bot` instead of `reports-staff`.** Rejected: gives the Bot credential (which serves unauthenticated public Reporter endpoints) full repository administration rights and attributes Staff role changes in GitHub's audit log to the Bot instead of the human System admin.
- **Call GitHub collaborator endpoints directly from the browser.** Rejected: leaves self-lockout and last-admin guards client-side only and pushes multi-call GitHub orchestration and error mapping outside the typed Worker API contract.
- **Also manage GitHub Organization membership and invitations.** Rejected: requires GitHub Organization `Members: read & write` and restricts the screen to GitHub Organization Owners only, splitting System admin (repo Admin) into two tiers.
- **Add GitHub Organization `Members: read` to detect GitHub Organization Owners proactively.** Rejected: adds a GitHub Organization-level permission without catching team-inherited roles; comparing `affiliation=all` against `affiliation=direct` plus a post-write effective-role check handles inherited access within repository permissions alone.

## Consequences

- `reports-bot` keeps its minimal `Metadata: read` + `Issues: write` blast radius. Viewers and Maintenance staff gain no new power from `reports-staff`'s added permission because GitHub intersects App permissions with the caller's own repo role, and every write is audited under the acting System admin's GitHub identity.
- Upgrading an existing Deployment requires approving `Administration: read & write` on `reports-staff` in GitHub, and already-signed-in System admins may need a one-time re-sign-in. A missing permission or stale token surfaces on the Staff screen as a dedicated `staff_permission_required` notice without disrupting Reports, Allowlist, or Configuration.
- Adding Staff is a single-user form taking a GitHub username (no email invites, no bulk paste). Existing GitHub Organization members get their role immediately (`204`); external GitHub accounts receive a free outside-collaborator repository invitation (`201`), managed in a Pending invitations section (edit role or cancel). Removing a Staff member revokes `reports` access (and GitHub automatically unassigns their open Reports), not wider GitHub Organization membership.
- The Worker enforces no self-demotion/self-removal and keeps at least one active effective System admin (counting inherited GitHub Organization Owners, never pending invitations). Inherited-only members (`all` minus `direct`) appear read-only; if an overlapping GitHub Organization or team grant overrides a direct edit or removal, the Worker surfaces an explicit warning.
- GitHub's code-only roles (`Write`, `Maintain`) stay collapsed into Maintenance staff with no GitHub code-role jargon, and are replaced with `pull`/`triage`/`admin` only when a System admin actively changes the member's dashboard role.
